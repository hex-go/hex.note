最近在公司的沙箱项目中遇到一个需求：用户希望把企业云文档像普通文件一样挂载给 Agent 使用，让 Agent 可以直接读取和处理文档内容。

Kubernetes 原生并没有针对这类业务文档的开箱即用挂载能力，因此我们需要定制 CSI 插件，把云文档以文件系统的形式暴露给 Pod 使用。

也正是这次实践，让我对 Kubernetes CSI 的整体链路有了更系统的认识。接下来这个系列，我会围绕“如何在 Kubernetes 中对 CSI 进行二次开发”展开，从容器存储基础、Linux mount、PV/PVC、CSI 协议，一直讲到如何实现一个可工作的 CSI Driver。

## 为什么 Kubernetes 需要 CSI？

在 Kubernetes 中，Pod 本身是临时资源，创建、删除、漂移都很频繁。为了让应用数据能够独立于 Pod 生命周期存在，Kubernetes 提供了 Volume、PV、PVC、StorageClass 等存储抽象。

从使用者视角来看，开发同学只需要声明：我需要一块多大的存储、挂载到容器的哪个目录、需要什么访问模式、由哪类存储系统提供。

但从集群实现视角来看，事情并没有这么简单。Kubernetes 需要真的去创建后端存储、格式化设备、挂载文件系统、把目录暴露给容器，并且在 Pod 删除、节点故障、扩容、快照等场景下完成对应的清理和恢复动作。

不同存储系统的实现方式完全不同。云盘需要调用云厂商 API 创建磁盘、挂载磁盘；NFS 需要把远端目录挂载到本机；Ceph RBD 需要映射块设备、格式化文件系统；对象存储、文档系统这类业务存储，又可能需要通过自定义逻辑把远端数据转换成文件系统视图。

如果每一种存储系统都直接写进 Kubernetes 核心代码里，Kubernetes 会变得越来越臃肿，存储厂商也很难独立发布、升级和维护自己的插件。

CSI（Container Storage Interface）就是为了解决这个问题而出现的。

它为 Kubernetes 和外部存储系统之间定义了一套标准接口。Kubernetes 不需要关心底层到底是云盘、NFS、Ceph，还是我们自己的云文档系统；它只需要按照 CSI 协议调用对应的 CSI Driver，由 Driver 去完成真正的创建、删除、挂载、卸载等操作。

可以简单理解为：

```
Pod / PVC
   ↓
Kubernetes 存储控制逻辑
   ↓
CSI 标准接口
   ↓
CSI Driver
   ↓
云盘 / NFS / Ceph / NAS / 云文档系统
```

这也是为什么我们要定制 CSI 插件：Kubernetes 原生并不知道“企业云文档”应该如何变成 Pod 里的文件，但只要我们实现一个符合 CSI 协议的 Driver，Kubernetes 就可以像管理其他存储一样，把它挂载给业务容器使用。

## 容器为什么需要卷？

在继续讲 CSI 之前，我们先回到一个更基础的问题：容器为什么需要卷？

容器镜像本身是只读的，容器启动后，运行时会在镜像层之上叠加一个可写层。应用在容器中创建、修改、删除文件时，实际上写入的是这个可写层，而不是镜像本身。

```
容器进程
  ↓
容器可写层
  ↓
只读镜像层
```

但这个可写层有一个明显的问题：它和容器生命周期绑定得太紧。

当容器被删除后，可写层也会随之删除。对于无状态应用来说，这通常不是问题；但对于需要保存数据的应用来说，就很危险了。例如日志文件、缓存数据、用户上传文件、数据库数据等，一旦只放在容器的可写层里，容器重建后就会丢失。

在 Kubernetes 中，Pod 又是一个比容器更高一层的临时调度单元。Pod 可能会因为节点故障、资源驱逐、版本发布、扩缩容等原因被删除和重建。如果应用数据只保存在容器的可写层里，那么 Pod 一旦重建，数据也就跟着消失了。

因此，Kubernetes 需要提供一种机制，让数据可以从容器可写层中独立出来，不再完全依赖容器本身的生命周期。

这个机制就是 Volume。

Volume 可以理解为一块额外挂载到容器中的存储空间。容器进程访问某个目录时，看到的不再只是容器自己的可写层，而是 Kubernetes 挂载进来的外部存储。

![图片](https://raw.githubusercontent.com/hex-go/hex.note/main/notedown/assets/0/0bbb7358fb0ff514/d738a2d8e128fb66fb34a446a147cc555215b157.png)

例如，我们可以把一个 Volume 挂载到容器的 `/data` 目录：

```
容器文件系统
├── /bin
├── /etc
├── /app
└── /data  <-- 挂载 Volume
```

这样应用写入 `/data` 的数据，就不再只是写进容器可写层，而是写入 Kubernetes 挂载进来的 Volume 中。

不过需要注意的是，Volume 是一个很大的概念，它并不等于持久化存储。不同类型的 Volume 生命周期并不一样：

所以，Kubernetes 之所以需要 Volume，本质上是为了解决两个问题：

*   让数据可以独立于容器可写层存在；
    
*   让容器能够通过标准路径访问外部存储。
    

而这个通过标准路径访问外部存储的动作，底层就离不开 Linux 的 `mount`。

## Linux mount 怎么工作？

在 Linux 中，我们平时看到的 `/`、`/data`、`/mnt`、`/var/lib/kubelet` 等路径，本质上都是挂载树上的一个个节点。所谓 `mount`，就是把一个文件系统、块设备、远端目录，或者某个已有目录，挂载到这棵目录树的某个路径上。

例如，我们可以把一块磁盘挂载到 `/data`：

```
$ mount /dev/vdb1 /data
```

也可以把一个 NFS 远端目录挂载到本地目录：

```
$ mount -t nfs 10.0.0.10:/data /mnt/nfs
```

挂载完成后，应用访问 `/mnt/nfs`，看到的就是远端 NFS Server 上的 `/data` 目录。

可以用 `findmnt` 查看挂载关系：

```
$ findmnt /mnt/nfs
TARGET   SOURCE          FSTYPE OPTIONS
/mnt/nfs 10.0.0.10:/data nfs4  rw,relatime,vers=4.1
```

这里最关键的是两个字段：

*   `TARGET`：本机挂载点，也就是应用访问的路径；
    
*   `SOURCE`：真正的数据来源，可以是块设备、远端目录，也可以是其他本地路径。
    

所以，`mount` 解决的核心问题是：让一个路径成为某个存储来源的访问入口。

这也是 Kubernetes Volume 的底层基础。应用容器里看到的是 `/data`，但 `/data` 背后真正指向哪里，要看 kubelet 或 CSI Driver 在节点上做了什么挂载操作。

```
容器内路径 /data
   ↓
节点上的挂载点
   ↓
emptyDir / hostPath / 云盘 / NFS / Ceph / 云文档系统
```

从这个角度看，Kubernetes 并没有发明一种全新的存储机制。它做的是把存储生命周期管理、调度、声明式 API 和 Linux 的挂载能力组合起来，让业务可以通过标准的 Pod 配置使用不同类型的存储。

## bind mount：为什么 CSI 离不开它？

除了普通 `mount`，Linux 中还有一种非常常见的挂载方式：`bind mount`。

普通 `mount` 通常是把磁盘分区、NFS、tmpfs 等存储来源挂载到某个目录，而 `bind mount` 则是把系统中已经存在的一个目录，重新挂载到另一个目录。

例如：

```
$ mkdir -p /data/source /data/target
$ echo "hello bind mount" > /data/source/hello.txt
$ mount --bind /data/source /data/target
```

挂载完成后，访问 `/data/target`，看到的就是 `/data/source` 中的内容：

```
$ ls /data/target
hello.txt

$ cat /data/target/hello.txt
hello bind mount
```

这时 `/data/source` 和 `/data/target` 并不是两份数据，而是同一份目录内容通过两个路径暴露出来。

这就是 `bind mount` 的核心特点：不创建新的文件系统；不复制目录内容，只是让一个已有路径在另一个位置再次出现，两个路径看到的是同一份底层数据。

它和普通 `mount` 的区别可以简单理解为：

需要注意的是，`bind mount` 挂载到目标目录后，目标目录原本的内容会被暂时遮蔽。例如：

```
$ echo "old file" > /data/target/old.txt
$ mount --bind /data/source /data/target
$ ls /data/target
hello.txt
```

这时看不到 `/data/target/old.txt`，因为 `/data/target` 已经被 `/data/source` 的内容覆盖成挂载点了。但文件并没有被删除，等执行 `umount /data/target` 后，原来的内容还会重新出现。

这个特性在 Kubernetes 中非常常见。

以 CSI 为例，很多 CSI Driver 并不是直接把后端存储一步挂进容器里，而是先在宿主机上完成准备工作，然后再通过 `bind mount` 把准备好的路径挂到 kubelet 指定的位置。可以简化理解为：

```
后端存储
  ↓
CSI Driver 在节点上准备好的路径
  ↓ bind mount
kubelet 指定的 Pod Volume 目标路径
  ↓
容器内的 mountPath
```

回到我们的场景，CSI Driver 最终要解决的也是类似问题：先把云文档系统中的内容转换成节点上的一个可访问目录，再把这个目录挂载到 Pod 中，让 Agent 像读取普通文件一样读取文档内容。

所以，理解 `bind mount`，其实就是在理解 CSI `NodePublishVolume` 的底层动作之一。

## emptyDir 和 hostPath：两个最简单的卷类型

理解了 `mount` 和 `bind mount` 后，我们再回到 Kubernetes，看看两个最简单的 Volume 类型：`emptyDir` 和 `hostPath`。

它们都不需要提前创建 PV / PVC，也不依赖外部存储系统，非常适合用来理解 Volume 的基本工作方式。

### emptyDir

`emptyDir` 是 Kubernetes 中最基础的临时卷。当 Pod 被调度到某个节点后，kubelet 会在该节点上为 Pod 创建一个空目录，并把这个目录挂载到容器指定路径中，典型路径类似：

```
/var/lib/kubelet/pods/<pod-uid>/volumes/kubernetes.io~empty-dir/<volume-name>
```

下面这个 Pod，会把一个 `emptyDir` 挂载到容器的 `/data` 目录：

```
apiVersion: v1
kind: Pod
metadata:
  name: emptydir-demo
spec:
  containers:
    - name: zlw-app
      image: busybox:1.36
      command: ["sh", "-c", "while true; do date >> /data/time.log; sleep 5; done"]
      volumeMounts:
        - name: emptydir-data
          mountPath: /data
  volumes:
    - name: emptydir-data
      emptyDir: {}
```

在这个例子中，容器每隔 5 秒会向 `/data/time.log` 写入当前时间。由于 `/data` 挂载的是 `emptyDir`，所以数据不会写到容器自己的可写层中，而是写到 kubelet 为这个 Pod 准备的临时目录里。

然后 kubelet 会把这个目录挂载到容器中声明的 `mountPath`，例如上面的 `/data` 路径。

`emptyDir` 的生命周期和 Pod 绑定：

*   容器重启：`emptyDir` 中的数据仍然存在；
    
*   Pod 删除：`emptyDir` 会被删除，里面的数据也会丢失；
    
*   Pod 被重新调度到其他节点：会重新创建一个新的 `emptyDir`。
    

因此，`emptyDir` 适合用于 Pod 内部的临时数据，例如缓存文件、多容器之间共享文件等，但不适合保存需要长期保留的数据。

### hostPath

`hostPath` 则是把宿主机上的某个目录或文件挂载到容器中。

例如下面这个 Pod，会把节点上的 `/var/log` 挂载到容器的 `/host-log` 目录：

```
apiVersion: v1
kind: Pod
metadata:
  name: hostpath-demo
spec:
  containers:
    - name: zlw-app
      image: busybox:1.36
      command: ["sh", "-c", "ls /host-log && sleep 3600"]
      volumeMounts:
        - name: host-log
          mountPath: /host-log
          readOnly: true
  volumes:
    - name: host-log
      hostPath:
        path: /var/log
        type: Directory
```

在这个例子中，容器访问 `/host-log`，实际上看到的是宿主机上的 `/var/log` 目录。

和 `emptyDir` 不同，`hostPath` 的数据并不跟随 Pod 删除而删除。只要宿主机上的目录还在，数据就还在。但它也会带来使用风险：一方面，Pod 会和节点本地路径产生更强绑定；另一方面，如果挂载了敏感宿主机目录，也可能带来安全风险。

所以 `hostPath` 通常用于一些特殊场景，例如：

*   日志采集组件读取节点日志；
    
*   节点监控组件读取宿主机指标文件；
    
*   CSI 插件或系统组件访问宿主机目录；
    
*   调试时临时查看节点文件。
    

在普通的业务应用中，不建议随意使用 `hostPath`。

### emptyDir 和 hostPath 的区别

我们可以简单对比一下：

只不过，对于 `emptyDir` 来说，这个位置是 kubelet 为 Pod 创建的临时目录；对于 `hostPath` 来说，这个位置是宿主机上的某个路径；而对于 CSI 来说，这个位置可能是云盘、NAS、Ceph，也可能是我们自己实现出来的云文档文件系统。

## 从 mount 看 NodePublishVolume

前面讲了这么多 `mount`、`bind mount`、`emptyDir` 和 `hostPath`，并不是为了单独补 Linux 基础，而是因为 Kubernetes 在使用外部存储时，最终也要落到类似的挂载动作上。

在 CSI 中，节点侧真正负责把 Volume 挂到 Pod 可访问路径的接口，叫做 `NodePublishVolume`。

这个名字第一次看可能有点抽象，但它做的事情并不神秘：当 Pod 需要 Volume 并且准备在某个节点上启动时，kubelet 会调用 CSI Driver，把这个 Pod 需要的 Volume 挂载到 kubelet 指定的目标路径。

我们先不用着急记住 CSI 的完整调用链，只需要抓住一个核心问题：

当 kubelet 已经决定要在当前节点启动 Pod 时，这个 Pod 声明的 Volume 应该如何出现在容器的 `mountPath` 中？

`NodePublishVolume` 要解决的就是这个问题。

在这个过程中，最关键的是 `target_path`。这个路径通常位于 kubelet 的工作目录下，类似：

```
/var/lib/kubelet/pods/<pod-uid>/volumes/kubernetes.io~<csi-name>/<volume-name>/mount
```

CSI Driver 要做的，就是把真正的数据来源挂载到这个 `target_path` 上。

但从 kubelet 的视角来看，这些差异都被 CSI Driver 屏蔽了。kubelet 不需要知道后端到底是 NFS、云盘、Ceph，还是公司的云文档系统。它只需要把目标路径交给 Driver，然后等待 Driver 把这个路径准备好。可以简单理解为：

```
kubelet
  ↓ 调用 NodePublishVolume
CSI Driver
  ↓ mount / bind mount / 自定义挂载逻辑
target_path
  ↓
Pod 中的 mountPath
```

当 `NodePublishVolume` 成功返回后，kubelet 就可以继续完成后续容器启动流程。最终，在容器内访问 `/data` 这类 `mountPath` 时，看到的就是 CSI Driver 挂载进去的内容。

因此，从 `mount` 的角度来看，`NodePublishVolume` 做的事情非常具体：在当前节点上，把某个 Volume 对应的数据来源，挂载到 kubelet 指定的目标路径。

回到开头的云文档场景：业务组想把企业云文档挂给 Agent 用，归根结底也是同样的路数——先把云文档系统里的内容，变成节点上一个可访问的目录，再通过挂载交给 Pod。只要这一步通了，云文档和云盘、NFS 等存储一样，都可以通过 CSI 接入 Kubernetes，并以 Volume 的形式交给业务容器使用。

## 小结

本期是 Kubernetes CSI 系列的第一期。我们先从业务场景出发，解释了为什么 Kubernetes 需要 CSI：当底层存储从云盘、NFS、Ceph 扩展到企业云文档这类业务系统时，Kubernetes 需要通过一套标准接口，把不同存储系统接入进来。

接着，我们从容器可写层、Volume、`emptyDir`、`hostPath` 一路讲到 Linux 的 `mount` 和 `bind mount`。无论是哪种 Volume，本质上都是让容器中的某个路径，指向容器外部的某块存储位置。

最后，我们从 `mount` 的角度初步理解了 CSI 中的 `NodePublishVolume`：它要做的就是在当前节点上，把 Volume 对应的数据来源挂载到 kubelet 指定的目标路径，最终交给 Pod 使用。
